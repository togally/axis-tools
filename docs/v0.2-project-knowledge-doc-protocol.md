# Axis v0.2 Project Knowledge Document Protocol

Axis v0.2 defines source-controlled project knowledge for architecture, business domains, feature design, task execution, version iteration, and document drift. Reader-facing design documents use Markdown and diagrams; YAML is reserved for metadata and machine indexes.

The protocol is public-safe: do not invent facts or expose credentials, private URLs, raw production logs, customer data, account identifiers, or internal issue links.

## Standards Baseline

- `ISO/IEC/IEEE 42010:2022` for architecture stakeholders, concerns, viewpoints, models, correspondences, decisions, and rationale.
- `arc42` for technical architecture structure.
- `C4` for context, container, optional component, dynamic, and deployment views.
- `ISO/IEC 25010:2023` for measurable quality scenarios.
- TOGAF Business Architecture and ArchiMate-lite for capabilities, value streams, processes, objects, and mappings.
- `GB/T 8567-2006` for Chinese formal-document completeness.
- ISO/IEC/IEEE 15289:2019 for lifecycle, revision, review, maintenance, and supersession.
- `IEEE 1016-2009` for applicable software design description concepts without claiming active-standard certification.

## Canonical Repository Layout

```text
.axis/docs/orgs/{organization_id}/projects/{project_slug}/
|-- metadata.yaml
|-- architecture/
|   |-- technical.md
|   `-- business.md
|-- business/
|   |-- inventory.yaml
|   `-- domains/
|       `-- {business_id}/
|           |-- detailed-design.md
|           |-- requirements/
|           |   `-- {requirement_id}/
|           |       `-- detailed-design.md
|           `-- features/
|               `-- {feature_id}/
|                   `-- detailed-design.md
|-- gaps/
|   `-- doc-gap-report.md
|-- tasks/
|   `-- {task_id}.task_execution_record.yaml
|-- versions/
|   `-- {version_id}.version_iteration_record.yaml
`-- drift/
    `-- {run_id}.affected_docs.yaml
```

The domain invariant is **one document per business_id** at `business/domains/{business_id}/detailed-design.md`.

## Sources Of Truth

- `architecture/technical.md` explains the global technical architecture.
- `architecture/business.md` explains global business goals, capabilities, value streams, domain boundaries, collaborations, and business risks.
- `business/inventory.yaml` is the unique machine-readable list of business domains and the execution index.
- Each `business_domain_detailed_design` is the source of truth for one domain's detailed business and implementation design.
- `gaps/doc-gap-report.md` records missing, stale, conflicting, blocked, and low-confidence knowledge.
- `metadata.yaml` records language, lifecycle, evidence baseline, revisions, checksums, confidence, supersession, and package linkage.
- Every factual claim cites repository or approved human evidence, or is explicitly an assumption or missing evidence.

## Skill Responsibilities

| Skill | Reads | Writes |
| --- | --- | --- |
| `axis-project-knowledge-bootstrap` | Routes, controllers, pages, menus, services, entities, migrations, tests, config, docs, and current Axis knowledge. | `project_technical_architecture`, `project_business_architecture`, `business_inventory`, one `business_domain_detailed_design` per domain, `doc_gap_report`, and metadata. |
| `axis-business-domain-doc` | Existing designs or one requirement, one `business_id`, inventory, global architecture, and repository evidence. | A reconciled `business_domain_detailed_design` or one `requirement_detailed_design`, plus a reviewed business-architecture summary revision. |
| `axis-feature-detailed-design` | One feature query, repository evidence, owning domain, project/domain knowledge, and explicit resolution confirmation. | One `feature_detailed_design`; nothing when resolution is absent or ambiguous. |
| `axis-doc-drift-capture` | Completed task/PR evidence, changed files, verification, and current project knowledge. | `task_execution_record`, `version_iteration_record`, and `affected_docs`. |

## Global Architecture Viewpoints

### Context Viewpoint

Capture system boundary, stakeholders, external systems, responsibilities, trust boundaries, and major flows with a C4 System Context diagram and interface table.

### Container And Building-Block Viewpoints

Capture executable units, data stores, technology, APIs, dependencies, and ownership with a C4 Container diagram and arc42 building-block view. Deeper decomposition is evidence-driven.

### Runtime And Deployment Viewpoints

Capture critical transactions, state changes, idempotency, concurrency, async behavior, failures, retries, compensation, runtime nodes, network boundaries, environments, and operational dependencies. Missing deployment evidence becomes a gap.

### Data And Quality Viewpoint

Capture ownership, migrations, cache/search consistency, retention, security, reliability, performance, maintainability, and observability with measurable ISO quality scenarios.

## `project_technical_architecture`

Required content: goal, readers, scope, concerns, measurable quality goals, constraints, context, solution strategy, containers, building blocks, runtime, data, deployment, crosscutting concepts, decisions, risks, technical debt, evidence, and glossary. A directory or dependency list is evidence, not a complete architecture document.

## `project_business_architecture`

Required content: business scope/non-goals, background, goals, stakeholders, roles, layered capability map, value streams, processes, exception paths, objects, information flows, rules, states, permissions, domain boundaries, capability-to-system mappings, external collaborations, risks, open questions, inventory navigation, evidence, and glossary.

Controllers, packages, tables, databases, and vendor products are not business capabilities; they may appear as evidence or system-support mappings.

Each item has a unique `business_id` and independently selectable evidence:

Allowed `document_status` / `doc_status` values are `missing`, `draft`, `review`, `approved`, `low_confidence`, `stale`, `blocked`, and `not_applicable`.

## `business_domain_detailed_design`

Purpose: transform one business-domain boundary from global architecture and inventory into an evidence-backed design that can be reviewed, implemented, tested, operated, and further decomposed into confirmed features.

Required content:

1. Design conclusion, scope, non-goals, readers, `business_id`, upstream revisions, and evidence baseline.
2. Domain responsibilities, direct collaborations, preconditions, completion conditions, and boundary decisions.
3. Actors, RACI, permissions, data scope, tenancy, and governance controls.
4. Main flow, branches, failure semantics, exception paths, recovery, compensation, and ownership.
5. Business objects, authority, lifecycle, state transitions, validations, rules, and user-visible results.
6. Inputs, outputs, interfaces, events, jobs, duplicate/ordering behavior, idempotency, concurrency, transaction, and consistency.
7. Capability/process-to-system mapping for entrypoints, services, data objects, dependencies, configuration, and tests.
8. Security, privacy, audit, observability, operational responsibility, rollout, rollback, and compatibility.
9. Acceptance traceability, assumptions, missing evidence, gaps, evidence index, and feature navigation.

The document references global architecture rather than copying descriptive paragraphs. It must not expand another domain's internal design. Policies, permissions, states, thresholds, contracts, or compensation rules without repository or approved human evidence remain unresolved and must not be invented.

## Detailed-Design Operating Modes

### `scan_and_reconcile`

Scan existing detailed designs, accepted requirement documents, design notes, API specifications, implementation, and tests. Classify existing documents as current, stale, conflicting, duplicated, orphaned, or reusable evidence. Resolve each reusable source to one `business_id`; `zero_matches` and `multiple_matches` stop the affected reconciliation and require user confirmation.

Supplement the canonical `business_domain_detailed_design`, preserve superseded source history, and create a reviewed `project_business_architecture` revision summarizing newly evidenced domain boundaries, capabilities, value streams, collaborations, business objects, risks, and document navigation. Global architecture contains the summary and cross-reference, not copied domain detail.

### `requirement_design`

Normalize one new or changed requirement into goal, actors, scope, non-goals, business outcome, constraints, acceptance criteria, and approved decisions. Resolve exactly one owning `business_id` before writing. If ownership is absent or ambiguous, stop and ask the user.

Write one `requirement_detailed_design` at:

```text
.axis/docs/orgs/{organization_id}/projects/{project_slug}/business/domains/{business_id}/requirements/{requirement_id}/detailed-design.md
```

The requirement document contains source/confirmation, current-versus-target behavior, impacted capabilities, requirement-specific flows, rules, objects, interfaces, data/state changes, compatibility/migration, delivery slices, tests, acceptance traceability, assumptions, missing evidence, and architecture impact. Add only a navigation/impact summary to the canonical domain design, then create a reviewed business-architecture revision summarizing changes to goals, capabilities, value streams, domain relationships, objects, risks, and gaps.

`requirement_design` does not replace one document per business_id or the feature confirmation gate. Missing or conflicting rules, permissions, states, thresholds, ownership, or acceptance meaning require user confirmation rather than invented design.

## `doc_gap_report`

Required content: executive conclusion, standards coverage matrix, stable gap table, prioritized remediation waves, and exit criteria. Each gap records standard/section, scope, type, severity, impact, evidence, recommended action, blocking source, and owner role.

## `feature_detailed_design`

One confirmed feature document records purpose, scope, requirements, non-goals, code map, actors, permissions, main/exception flows, interfaces, state/data design, module responsibilities, algorithms, validation/errors, transactions, idempotency, concurrency, dependencies, cache/consistency, security/privacy/audit, observability, tests, acceptance, rollout, rollback, compatibility, decisions, assumptions, and missing evidence.

## Feature Resolution Confirmation Gate

Before writing `feature_detailed_design`, search routes, controllers, pages, menus, services, entities, migrations, tests, config, docs, and existing Axis knowledge. Classify exactly one result:

- `zero_matches`: no connected entrypoint and implementation evidence. Write nothing; report searched scope and ask for a route, page/menu text, screenshot, class/method, API path, table/event/job, source path, or approved wording.
- `multiple_matches`: multiple candidates remain. Write nothing; present evidence-backed candidates and ask the user to choose.
- `confirmed_feature`: evidence connects a concrete entrypoint to implementation, and the user explicitly identified or confirmed it.

Even one strong match needs an explicit resolution summary and user confirmation when the original target is not exact. Retain the confirmation, evidence, timestamp, and selected `business_id`. Do not fabricate confirmation or guess domain ownership.

The feature path is:

```text
.axis/docs/orgs/{organization_id}/projects/{project_slug}/business/domains/{business_id}/features/{feature_id}/detailed-design.md
```

## Lifecycle Documents

- `task_execution_record` captures changed files, verification, risks, follow-up items, and completion evidence.
- `version_iteration_record` captures objectives, tasks, capability changes, verification, release gate, rollback notes, risks, and follow-ups.
- `affected_docs` classifies drift as `unchanged`, `needs_revision`, `stale`, `missing`, `conflict`, or `not_applicable`.

Generated reader-facing documents remain `review` until an authorized human approves them. Supersession is explicit and history is preserved.

## Project Knowledge Snapshot And OSS Sync

`axis project-knowledge-capture` validates the canonical project source root, requires one domain detailed design for every inventory ID, and writes a local snapshot. It does not publish.

For a project-document snapshot, reader-facing source paths synchronize directly under:

```text
{prefix}/orgs/{organization_id}/projects/{project_slug}/
```

Control files synchronize to `projects/{project_slug}/_sync/metadata.json` and `projects/{project_slug}/_sync/manifest.json`, with the manifest last. Metadata exposes `project_document_path`. A later reviewed snapshot updates the same project-document paths.

General immutable packages synchronize under:

```text
{prefix}/orgs/{organization_id}/projects/{project_slug}/packages/{run_id}/
```

Always run `axis oss-publish --dry-run` before an authorized upload. Never create buckets, credentials, public approval, or remote deletions as an implicit side effect.

## Verification

- Parse metadata/inventory YAML and validate unique `business_id` values.
- Require inventory count to equal canonical domain detailed-design count.
- Render Mermaid and validate required sections.
- Check role separation and paragraph duplication.
- Check every factual claim for evidence or explicit uncertainty.
- Scan for placeholders, credentials, private URLs, raw logs, and customer identifiers.
- Verify snapshot manifests, checksums, direct project paths, and last-uploaded sync manifest.
