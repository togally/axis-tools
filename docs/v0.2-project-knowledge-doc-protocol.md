# Axis v0.2 Project Knowledge Document Protocol

Axis v0.2 defines source-controlled project knowledge for architecture, level-1 and secondary business capabilities, feature design, task execution, version iteration, and document drift. Reader-facing design documents use Markdown and diagrams; YAML is reserved for metadata and machine indexes.

The protocol is public-safe: do not invent facts or expose credentials, private URLs, raw production logs, customer data, account identifiers, or internal issue links.

Reader-facing Markdown horizontal tables have at most six columns and are reserved for compact, atomic comparisons. Records containing long repository paths, evidence anchors, links, code contracts or several prose-heavy fields use individual `项目 / 内容` vertical tables, or compact tables joined by the same stable ID. Presentation changes must preserve every identity, semantic and traceability field. Literal pipe characters inside cells are escaped. Dashboard horizontal scrolling is a fallback for unusual content, not permission to retain a wide source table.

## Standards Baseline

- `ISO/IEC/IEEE 42010:2022` for architecture stakeholders, concerns, viewpoints, models, correspondences, decisions, and rationale.
- `arc42` for technical architecture structure.
- `C4` for context, container, optional component, dynamic, and deployment views.
- `ISO/IEC 25010:2023` for measurable quality scenarios.
- TOGAF Business Architecture and ArchiMate-lite for capabilities, value streams, processes, objects, and mappings.
- `GB/T 8567-2006` for Chinese formal-document completeness.
- ISO/IEC/IEEE 15289:2019 for lifecycle, revision, review, maintenance, and supersession.
- `IEEE 1016-2009` for applicable software design description concepts without claiming active-standard certification.

## Canonical Repository Layout

```text
.axis/docs/orgs/{organization_id}/projects/{project_slug}/
|-- metadata.yaml
|-- architecture/
|   |-- technical.md
|   `-- business.md
|-- business/
|   |-- inventory.yaml
|   |-- level1-capability-dependency-graph.yaml
|   `-- capabilities/
|       `-- {level1_capability_id}/
|           |-- detailed-design.md
|           |-- secondary-capabilities/
|           |   `-- {secondary_capability_id}/
|           |       `-- detailed-design.md
|           |-- requirements/
|           |   `-- {requirement_id}/
|           |       |-- master-draft.md
|           |       `-- detailed-design.md
|           `-- features/
|               `-- {feature_id}/
|                   `-- detailed-design.md
|-- gaps/
|   `-- doc-gap-report.md
|-- tasks/
|   `-- {task_id}.task_execution_record.yaml
|-- versions/
|   `-- {version_id}.version_iteration_record.yaml
`-- drift/
    `-- {run_id}.affected_docs.yaml
```

The capability hierarchy has one overview per `level1_capability_id` at `business/capabilities/{level1_capability_id}/detailed-design.md` and one independent detailed design per declared secondary capability at `business/capabilities/{level1_capability_id}/secondary-capabilities/{secondary_capability_id}/detailed-design.md`. The overview is a level-1 interface-detail panorama: it contains every secondary capability as a summary and canonical link; one model-derived `3.N` group per actual external business capability with fixed `3.N.1/.2/.3` order, a secondary-capability-node/API-and-complete-interface-edge Mermaid and per-hop vertical trace including parent `table_id`; a professional business-term dictionary; and the mandatory level-1 table inventory, physical-table ER, relationship evidence and per-table field design. One overview `journey_id` may cross multiple participating children, each of which repeats it as `level1_journey_id` and binds its local hop to a `flow_id` and/or `api_id`. `business_id` values map secondary capabilities to business and implementation evidence; they are not document boundaries.

Historical revisions are stored outside the current tree:

```text
.axis/docs/_archive/orgs/{organization_id}/projects/{project_slug}/{canonical_path}.history/{archive_id}/
|-- document{extension}
`-- metadata.json
```

The current canonical path never changes merely because history exists. Normal document lists read `.axis/docs/orgs/`; archive-aware tools read `_archive` separately.

## Sources Of Truth

- `architecture/technical.md` explains the global technical architecture.
- `architecture/business.md` explains global business goals, capabilities, value streams, business boundaries, collaborations, and business risks.
- `business/inventory.yaml` is the unique machine-readable hierarchy of level-1 capabilities, secondary capabilities, and their `business_id` evidence mappings.
- `business/level1-capability-dependency-graph.yaml` is the unique project-wide machine source for evidence-backed level-1 upstream/downstream relationships. Dashboard may render it as a tree view, while overview documents retain only direct incoming/outgoing projections.
- Each `business_capability_detailed_design` is the source of truth for one level-1 external-business-capability/interface-implementation panorama, integrated cross-secondary logic, professional terminology, level-1 table/ER design and child navigation.
- Each `secondary_capability_detailed_design` is the source of truth for one secondary capability's complete business and per-contract internal code-flow, transaction, quality, security, test and acceptance design, indexed back to its parent `journey_id` values.
- `gaps/doc-gap-report.md` records missing, stale, conflicting, blocked, and low-confidence knowledge.
- `metadata.yaml` records language, lifecycle, evidence baseline, revisions, checksums, confidence, supersession, and package linkage.
- Every factual claim cites repository or approved human evidence, or is explicitly an assumption or missing evidence.

## Global Architecture Viewpoints

### Context Viewpoint

Capture system boundary, stakeholders, external systems, responsibilities, trust boundaries, and major flows with a C4 System Context diagram and interface table.

### Container And Building-Block Viewpoints

Capture executable units, data stores, technology, APIs, dependencies, and ownership with a C4 Container diagram and arc42 building-block view. Deeper decomposition is evidence-driven.

### Runtime And Deployment Viewpoints

Capture critical transactions, state changes, idempotency, concurrency, async behavior, failures, retries, compensation, runtime nodes, network boundaries, environments, and operational dependencies. Missing deployment evidence becomes a gap.

### Data And Quality Viewpoint

Capture ownership, migrations, cache/search consistency, retention, security, reliability, performance, maintainability, and observability with measurable ISO quality scenarios.

## `project_technical_architecture`

Required content: goal, readers, scope, concerns, measurable quality goals, constraints, context, solution strategy, containers, building blocks, runtime, data, deployment, crosscutting concepts, decisions, risks, technical debt, evidence, and glossary. A directory or dependency list is evidence, not a complete architecture document.

## `project_business_architecture`

Required content: business scope/non-goals, background, goals, stakeholders, roles, layered capability map, project-level dependency-graph/tree view and derivation status, value streams, processes, exception paths, objects, information flows, rules, states, permissions, domain boundaries, capability-to-system mappings, external collaborations, risks, open questions, inventory navigation, evidence, and glossary.

Controllers, packages, tables, databases, and vendor products are not business capabilities; they may appear as evidence or system-support mappings.

## `business_inventory`

Each top-level item has a unique `level1_capability_id`. Its complete `secondary_capabilities` list defines the overview navigation and required child documents. Each secondary capability has a unique `secondary_capability_id` within the project and one or more `business_ids` for evidence mapping:

```yaml
level1_capabilities:
  - level1_capability_id: example_operations
    level1_capability_name: 示例经营
    summary: 基于证据的一级能力说明。
    secondary_capabilities:
      - secondary_capability_id: example_onboarding
        secondary_capability_name: 示例入驻
        business_ids:
          - example_application
          - example_review
        evidence_refs: []
        code_refs:
          routes: []
          controllers: []
          pages: []
          menus: []
          services: []
          entities: []
          migrations: []
          tests: []
          config: []
          docs: []
    doc_status: low_confidence
    confidence: medium
    confidence_reason: 命名和路由证据需要人工复核。
    doc_refs:
      project_technical_architecture: null
      project_business_architecture: null
      business_capability_detailed_design: null
    gap_items: []
    next_action: review_evidence
```

Allowed `document_status` / `doc_status` values are `missing`, `draft`, `review`, `approved`, `low_confidence`, `stale`, `blocked`, and `not_applicable`.

## `level1_capability_dependency_graph`

The canonical path is `business/level1-capability-dependency-graph.yaml`. Inventory defines the complete node identity set; this graph defines project-wide relationships. It is a directed dependency graph rather than a forced single-parent tree because a capability may have multiple upstreams and evidence-backed staged reverse relationships. Dashboard may unfold direct relationships as a tree view and must guard against revisiting a node.

The graph lifecycle is machine-checkable:

- `derivation_status=pending_level1_completion`, `derivation_method=model_synthesis`, `derivation_revision=not_derived`, one stable `gap_id` other than `not_applicable`, the full inventory node set and `edges: []` while any level-1 overview has `user_journey_coverage=partial` or any owning child has `interface_coverage=partial`;
- `derivation_status=derived`, a stable derivation revision and `gap_id=not_applicable` only after every level-1 and secondary document is complete and one project-level model pass has considered the complete current set;
- every derived edge contains a stable `edge_id`, `from_level1_capability_id`, `to_level1_capability_id`, `relation_type`, `stage`, summary, at least one `journey_id` or `api_id` that exists in its source/target capability, exact code or canonical-document evidence refs, and confidence; the business-architecture Mermaid/tree view preserves every `edge_id`;
- self edges, unknown nodes, duplicate edge IDs and duplicate `(from,to,relation_type,stage)` relationships are invalid. Multiple incoming/outgoing edges and evidence-backed staged reverse relationships are allowed.

Derived upstream for one capability is exactly the set of sources on its direct incoming edges. Derived downstream is exactly the set of targets on its direct outgoing edges. Ancestors, descendants and paths are traversal results, not copied into overview files. Any input boundary or relationship-evidence change invalidates local projections: archive the graph and affected overviews, return all projections to pending, rerun the global model synthesis after completeness is restored, then batch-update them.

## `business_capability_detailed_design`

Purpose: provide one evidence-backed level-1 interface-detail panorama. It answers which external business capabilities are actually provided, who uses each capability and for what goal, how one or more secondary capabilities collaborate through interfaces to implement it, what the user sees, which professional terms govern its meaning, and which persisted tables and relationships support it.

Required content:

1. A fixed reader structure: `1. 设计结论与能力边界`, `2. 二级能力完整性与导航`, `3. 对外业务能力与接口实现`, `4. 业务语义`, `5. 表结构设计`, `6. 缺口与覆盖说明`, `7. 文档完整性校验`, and `8. 文档导航与证据索引`. There is no independent `跨二级能力用户旅程`, `共享业务语义与一级治理` or navigation glossary chapter.
2. Design conclusion, scope, non-goals, readers, `level1_capability_id`, upstream revisions, evidence baseline, return-to-business-architecture link, adjacent level-1 links and a secondary-capability completeness matrix covering every `secondary_capabilities` item, mapped `business_ids`, status and canonical child link. “Previous/next” links are navigation only.
3. Machine-checkable `user_journey_design_status=detailed`, `user_journey_coverage=complete|partial` and `user_journey_gap_id` values once in the header, plus `table_design_status=detailed|not_applicable`, `table_design_coverage=complete|partial|not_applicable` and `table_design_gap_id` once at the start of Section 5. Complete journey/table coverage uses `not_applicable` gap IDs; partial coverage uses stable non-empty gap IDs and records missing scope, evidence, impact and remediation in Section 6 and the gap report.
4. A model pass over actual inventory, UI/menu, routes, APIs, events, jobs, commands, code and tests that creates one sequential `3.N` group for every externally provided business capability identified by user goal and visible result. Every group contains exactly one `3.N.1 业务说明`, `3.N.2 二级能力与接口实现逻辑` and `3.N.3 实现步骤` in that fixed order. A fixed list, one representative endpoint per module, one row per secondary capability and the legacy fourteen-column table are invalid.
5. Every `3.N.1 业务说明` is a vertical `项目 / 内容` table with exactly `journey_id`, 用户/角色, 提供的业务, 用户目标, 用户怎么操作, 用户可见结果, 参与二级能力 and 证据; its evidence includes at least one exact repository-relative anchor. Every `3.N.2` is an actual Mermaid logic graph organized around participating secondary-capability nodes. Each actual `api_id` and complete HTTP/event/job/command contract form the same implementation-edge label, never standalone nodes or loose text; multiple secondary nodes connect in the order declared by the steps.
6. Every `3.N.3 实现步骤` gives each ordered hop its own vertical `项目 / 内容` table with exactly `step_id`, `secondary_capability_id`, `api_id`, 接口/入口, Controller/Handler, Service/UseCase, 读取数据, 写入/产生数据, 读写 `table_id`, 二级能力详情 and 证据. Every step has concrete repository-relative `path:begin-end#symbol` anchors for Controller/Handler and Service/UseCase and at least one exact evidence anchor. It records one or more stable parent `table_id` values; exact no-persistence evidence is required for `not_applicable`. One `journey_id` may span multiple secondaries; its graph and steps contain the cross-secondary handoff.
7. Every participating child repeats the same parent `journey_id` as `level1_journey_id` and binds its local hop to the corresponding `flow_id` and/or `api_id`. A child cannot add an unpaired journey, and the parent cannot omit a participating child. A complete level-1 journey design requires `interface_coverage=complete` in every child.
8. Section 4 uses exactly 专业术语, 定义, 适用场景与边界, 易混淆术语及区别, 关联二级能力 and 权威来源/证据. It explains professional language rather than security, quality, release or operational governance.
9. Detailed Section 5 is fixed as `5.1 表清单`, `5.2 ER 图`, `5.2.1 ER 关系证据`, then continuous per-table subsections from `5.3` titled by actual physical table name. It uses the fixed inventory `table_id | 物理表名 | 业务实体/用途 | 所属二级能力 | 读写 api_id | 证据`, whose ID set equals exactly the deduplicated union of non-`not_applicable` Section 3 step table IDs; an evidence-backed ER diagram whose entities use the inventory's actual physical table names; and one `table_id`-controlled subsection per table with `字段 | 类型/可空/默认值 | 键/约束 | 业务语义 | 读写 api_id | 证据`. The combined type cell preserves all three labeled values. With multiple tables, the fixed `ER 关系证据` table is `relation_id | 表关系（主 -> 从） | 关系/基数 | 关联键 | 业务语义 | 证据`; its relation cell contains both stable table IDs, every table participates in at least one row, and every row has an exact relationship anchor. A single-table design explicitly records `ER 关系证据：not_applicable（单表，无需跨表关系）`. Every inventory, relationship and field evidence cell has an exact DDL/migration/ORM/Mapper/query `path:begin-end#symbol` anchor. Only exact evidence that no external capability reads or writes persisted data permits the retained Section 5 `not_applicable` reason/evidence vertical table.
10. Exactly one dependency projection control line with `dependency_graph_status`, `dependency_graph_revision` and `dependency_graph_gap_id`, plus upstream/downstream fields sourced only from `business/level1-capability-dependency-graph.yaml`. Pending uses `not_derived` for both directions. Derived uses only direct incoming/outgoing neighbors and `[]` for a confirmed empty direct set.

The journey coverage fields are authoring and capture metadata. Keep them in the overview header and gap evidence; do not expose a reader-facing `用户旅程覆盖契约` chapter in the generated level-1 document.

The overview references global architecture and child documents instead of copying request/response field dictionaries, full call chains, Mapper/Repository implementation, per-interface transaction/concurrency/performance/fault-tolerance detail or security/test/acceptance matrices. Those remain inside each participating child's owning `5.N` group. The level-1 table inventory, ER and physical-column dictionary are mandatory and authoritative across the participating secondaries. One representative interface per module is not complete coverage. The overview is also incomplete if an inventory secondary capability is omitted, duplicated, lacks a canonical child link or participates in no evidence-backed external business capability.

## `secondary_capability_detailed_design`

Purpose: hold the complete business and interface-oriented technical design for one `secondary_capability_id`, including responsibility, actors, permissions, main and exception flows, logical relations, code objects and dependencies, interfaces, events, jobs, transactions, concurrency, performance, fault tolerance, security, tests, acceptance, rollout, risks and evidence. Section 1 states the concise capability boundary; document identity remains in the header. Section 2 is the sole authoritative `调用主体、权限与接口矩阵` with fixed fields 主体/角色, 所需权限/策略, `api_id`, 可调用接口/能力, 数据范围 and 授权证据. Every Section 5 `api_id` has at least one matrix row, every matrix interface exactly matches Section 5, and no absent interface, generic permission, generic data scope or inferred role is allowed. Each material flow records a parent `level1_journey_id` whose parent `3.N` names this child as a participant, and binds it to the relevant `flow_id` and/or `api_id`. It then traces API/entrypoint, Controller/handler, Service/use case, Mapper/Repository, entity/physical table, the same parent `table_id` value or values as the owning parent step, and test using repository-relative `path:begin-end#symbol` anchors. Every `5.N.1` entity/table row contains those matching parent IDs, or exact-evidence `not_applicable` when the contract has no persisted-data touchpoint; absent internal evidence is recorded explicitly rather than inferred.

Section 3 is titled `能力级流程与跨接口关系` and is capability-oriented: it describes only ordering, triggers, state handoffs and compensation relationships across multiple interfaces, events, topics, jobs or commands. Individual contract validation, method calls, decisions, data reads/writes, result generation and failure handling belong to that contract's `5.N.2`. A capability without cross-contract orchestration records that conclusion and points to Section 5 instead of rendering a generic actor-to-API placeholder diagram.

Section 5 is contract-oriented. Every concrete HTTP interface, EVENT/TOPIC, JOB or COMMAND is one direct, sequential `### 5.N {contract_name}` group. Each group owns exactly `#### 5.N.1 接口清单与代码追溯`, `#### 5.N.2 内部处理逻辑`, `#### 5.N.3 请求字段`, `#### 5.N.4 响应字段`, `#### 5.N.5 错误码与异常映射`, `#### 5.N.6 认证与授权执行`, `#### 5.N.7 事务、并发、性能与容错`, and `#### 5.N.8 安全、测试与验收`; the numeric prefix must match the parent, so `5.2` owns `5.2.1` through `5.2.8`. The first subsection contains a compact `项目 / 内容` contract table and a separate `实现层 / 精确定位 / 职责` trace table instead of a single wide row. Its caller summary must agree with Section 2. The second contains a concrete processing summary plus an actual Mermaid flow/sequence/state diagram or compact step table, using real symbols, tables and states rather than generic nodes or retained placeholders. Request fields use `字段 | 位置 | 类型/必填 | 约束/枚举 | 业务语义/敏感处理 | 证据/状态`; response fields use `HTTP/消息/执行状态 | 字段 | 类型/可空 | 业务语义/产生位置 | 证据/状态`; combined cells retain every labeled source value. `5.N.6` explains the concrete authentication and authorization enforcement for the Section 2 relation without creating a second actor/role inventory. `5.N.7` owns transaction and consistency boundaries, idempotency, concurrency, performance/capacity, timeout, retry, compensation, degradation and observability. `5.N.8` owns non-authorization security controls, privacy/audit where applicable, test coverage, observable acceptance results and exact evidence or an explicit target plan. Multiple contracts may not share global logic, request, response, error, governance, quality or test sections.

The default secondary document must not contain top-level `## 实体、表与对象关系`, `## 表结构设计`, `## 事务、并发、性能与容错`, `## 安全、测试与验收`, or `## 端到端追溯矩阵` sections. Transaction/performance/fault-tolerance and security/test/acceptance concerns belong to each owning `5.N.7` and `5.N.8`; interface-to-code, local persisted-data and test traceability belongs to `5.N.1`, `5.N.2` and `5.N.8`. The complete table inventory, ER and per-table fields are mandatory in the parent level-1 Section 5 and are referenced by `table_id`, not duplicated into the secondary document. A deeper standalone database release/review document is created only when explicitly requested.

For EVENT/TOPIC contracts, request fields describe the envelope, key and payload while response fields describe acknowledgement, a result event or explicit one-way semantics. For JOB/COMMAND contracts, they describe execution context/parameters and result/status. A real contract without fields or a direct response keeps an evidence-backed `not_applicable` row; a whole interface design may use `not_applicable` only when the reason and exact repository evidence prove there is no callable interface, event, topic, job or command.

Every child returns to its level-1 overview and links to the previous and next secondary capability in stable identifier order. The level-1 overview returns to `architecture/business.md` and links to adjacent level-1 overviews. Dashboard may derive these controls from canonical paths, but retained Markdown links remain for portability.

## Project-Knowledge Operating Modes

### `bootstrap`

Create the first complete global architecture, inventory, a pending project dependency graph, one level-1 interface-detail panorama per `level1_capability_id`, one child detailed design per `secondary_capability_id`, plus the gap report and metadata set. Resolve journey and table-design states, model-derived external-business-capability groups, same-ID participant trace and the required table/ER design first. Only when all parent and child journey/interface coverage is complete may one project-wide model pass derive the graph and batch-project direct upstream/downstream into every overview.

### `scan_and_reconcile`

Scan existing detailed designs, accepted requirement documents, design notes, API specifications, implementation, and tests. Classify existing documents as current, stale, conflicting, duplicated, orphaned, or reusable evidence. Resolve each reusable source to one `level1_capability_id` and at least one `secondary_capability_id`; map its `business_ids` as evidence. `zero_matches` and `multiple_matches` stop the affected reconciliation and require user confirmation.

Supplement the affected child designs and the canonical overview's owning `3.N` business-capability groups, implementation steps, journey/table coverage gaps, terminology, table/ER design, summary and navigation; preserve same-ID participating-child trace and superseded source history; and create a reviewed `project_business_architecture` revision only for global impact. When level-1 boundaries or relationship evidence changes, invalidate the graph and all affected projections, then re-derive them globally after the completeness gate. Global architecture contains summaries and cross-references, not copied child detail.

### `requirement_design`

Normalize one new or changed requirement into goal, actors, scope, non-goals, business outcome, constraints, acceptance criteria, and approved decisions. Resolve exactly one owning `level1_capability_id` and at least one `secondary_capability_id` before writing; retain mapped `business_ids` for evidence. If ownership is absent or ambiguous, stop and ask the user.

Write one `requirement_detailed_design` at:

```text
.axis/docs/orgs/{organization_id}/projects/{project_slug}/business/capabilities/{level1_capability_id}/requirements/{requirement_id}/detailed-design.md
```

The requirement document contains source/confirmation, current-versus-target behavior, impacted secondary capabilities, requirement-specific flows, rules, objects, interfaces, data/state changes, compatibility/migration, delivery slices, tests, acceptance traceability, assumptions, missing evidence, and architecture impact. Update every participating child design and its same-ID journey trace; update the overview's owning `3.N` group, implementation steps, journey/table coverage, terminology, table/ER design and navigation when the operation or persistence changes; then revise business architecture only when global goals, capability boundaries, value streams or relationships change.

`requirement_design` does not replace the overview/child hierarchy or the feature confirmation gate. Missing or conflicting rules, permissions, states, thresholds, ownership, or acceptance meaning require user confirmation rather than invented design.

## Development-Document Operating Modes

- `existing_feature_export`: output requested documents for one resolved existing feature without changing code or canonical documents unless asked.
- `planned_feature_generation`: discover an unimplemented code-changing feature, approve one `master_draft`, then expand it.
- `implemented_feature_correction`: archive and correct stale or wrong documents against implemented behavior; switch to iteration if behavior/code must change.
- `implemented_feature_iteration`: discover and approve a code-changing iteration, archive affected canonical documents, and create reviewed revisions.

For planned generation and implemented iteration, discovery covers product, architecture, performance, business flow, database design, and market only when market evidence can change scope or acceptance. Unknown answers receive a recommended option and trade-offs. Downstream documents cannot expand until the user explicitly approves the `master_draft`.

## `doc_gap_report`

Required content: executive conclusion, standards coverage matrix, stable gap table, prioritized remediation waves, and exit criteria. Each gap records standard/section, scope, type, severity, impact, evidence, recommended action, blocking source, and owner role.

## `feature_detailed_design`

One confirmed feature document records purpose, scope, requirements, non-goals, code map, actors, permissions, main/exception flows, interfaces, state/data design, module responsibilities, algorithms, validation/errors, transactions, idempotency, concurrency, dependencies, cache/consistency, security/privacy/audit, observability, tests, acceptance, rollout, rollback, compatibility, decisions, assumptions, and missing evidence.

## Feature Resolution Confirmation Gate

Before writing `feature_detailed_design`, search routes, controllers, pages, menus, services, entities, migrations, tests, config, docs, and existing Axis knowledge. Classify exactly one result:

- `zero_matches`: no connected entrypoint and implementation evidence. Write nothing; report searched scope and ask for a route, page/menu text, screenshot, class/method, API path, table/event/job, source path, or approved wording.
- `multiple_matches`: multiple candidates remain. Write nothing; present evidence-backed candidates and ask the user to choose.
- `confirmed_feature`: evidence connects a concrete entrypoint to implementation, and the user explicitly identified or confirmed it.
- `confirmed_planned_feature`: code absence is expected; the user confirms stable feature/domain identity, product goal, scope, non-goals, and acceptance boundary.

Even one strong match needs an explicit resolution summary and user confirmation when the original target is not exact. Retain the confirmation, evidence, timestamp, selected `level1_capability_id`, affected `secondary_capability_id` values, and mapped `business_ids`. Do not fabricate confirmation or guess capability ownership.

The feature path is:

```text
.axis/docs/orgs/{organization_id}/projects/{project_slug}/business/capabilities/{level1_capability_id}/features/{feature_id}/detailed-design.md
```

## Document Archive And Revision

Before any current canonical document is modified, `axis-doc-development` creates an exact immutable snapshot and `axis.document_archive` metadata under `_archive`. Metadata records canonical path, archive ID, time, reason, request summary, source/target revisions, and SHA-256.

Archive creation is blocking: a failed snapshot or hash check stops the modification. `approved` documents are never changed in place; a new `review` revision records `supersedes`. The dashboard exposes archive history separately from current documents and provides an explicit return-to-current action.

## Lifecycle Documents

- `task_execution_record` captures changed files, verification, risks, follow-up items, and completion evidence.
- `version_iteration_record` captures objectives, tasks, capability changes, verification, release gate, rollback notes, risks, and follow-ups.
- `affected_docs` classifies drift as `unchanged`, `needs_revision`, `stale`, `missing`, `conflict`, or `not_applicable`.

Generated reader-facing documents remain `review` until an authorized human approves them. Supersession is explicit and history is preserved.

## Project Knowledge Snapshot And OSS Sync

`axis project-knowledge-capture` validates the canonical project source root, requires one overview for every inventory `level1_capability_id` and one detailed design for every `secondary_capability_id`, validates parent/child completeness and business mappings, and writes a local snapshot. It does not publish.

For a project-document snapshot, reader-facing source paths synchronize directly under:

```text
{prefix}/orgs/{organization_id}/projects/{project_slug}/
```

Control files synchronize to `projects/{project_slug}/_sync/metadata.json` and `projects/{project_slug}/_sync/manifest.json`, with the manifest last. Metadata exposes `project_document_path`. A later reviewed snapshot updates the same project-document paths.

General immutable packages synchronize under:

```text
{prefix}/orgs/{organization_id}/projects/{project_slug}/packages/{run_id}/
```

Always run `axis oss-publish --dry-run` before an authorized upload. Never create buckets, credentials, public approval, or remote deletions as an implicit side effect.
