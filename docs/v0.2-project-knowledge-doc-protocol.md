# Axis v0.2 Project Knowledge Document Protocol

Axis v0.2 defines the repository document protocol used by the project knowledge skills. It adds a source-controlled project knowledge layer on top of the v0.1 package and outbox contract. It does not change the v0.1 package files, the private_beta release gate, or the rule that OSS credentials are read only from environment variable names declared in `.axis/config.yml`.

## Scope

The protocol standardizes how an existing project records architecture, business domains, task execution, version iteration, and document drift. It is designed for public-safe repository source. It must not contain secrets, private URLs, raw production logs, customer data, or account details.

The canonical root is:

```text
.axis/docs/projects/{project_slug}
```

Recommended layout:

```text
.axis/docs/projects/{project_slug}/
|-- project_technical_architecture.md
|-- project_business_architecture.md
|-- business_inventory.yaml
|-- doc_gap_report.yaml
|-- domains/
|   `-- {business_id}/
|       |-- domain_business_spec.md
|       `-- domain_technical_design.md
|-- tasks/
|   `-- {task_id}.task_execution_record.yaml
|-- versions/
|   `-- {version_id}.version_iteration_record.yaml
`-- drift/
    `-- {run_id}.affected_docs.yaml
```

## Skill Responsibilities

| Skill | Reads | Writes |
| --- | --- | --- |
| `axis-project-knowledge-bootstrap` | Repository evidence such as routes, controllers, pages, services, entities, migrations, tests, config, and docs. | `project_technical_architecture`, `project_business_architecture`, `business_inventory`, and `doc_gap_report`. |
| `axis-business-domain-doc` | One `business_id`, `business_inventory`, repository evidence, and existing project architecture docs. | `domain_business_spec` and `domain_technical_design` for that `business_id`. |
| `axis-doc-drift-capture` | Completed task or PR evidence, changed files, verification commands, and existing project knowledge docs. | `task_execution_record`, `version_iteration_record`, and `affected_docs`. |

Each skill must cite evidence paths when making assertions. If evidence is missing or conflicting, the output records `missing_evidence`, `assumptions`, or `conflict` instead of inventing facts.

## Core Document Types

### `project_technical_architecture`

Purpose: capture the current global technical architecture of the repository.

Required sections:

- runtime_stack
- module_map
- data_store_map
- integration_map
- deployment_and_config
- observability
- security_boundaries
- evidence_refs
- open_questions

### `project_business_architecture`

Purpose: capture global business capabilities and their relationships without exposing private customer details.

Required sections:

- business_context
- actor_roles
- capability_map
- cross_domain_flows
- permission_model_summary
- risk_and_compliance_notes
- evidence_refs
- open_questions

### `business_inventory`

Purpose: provide a stable list of business domains that downstream skills can address by `business_id`.

Each item includes:

```yaml
business_id: billing
name: Billing
aliases:
  - invoice
status: active
document_status: missing
criticality: high
actors:
  - account_user
entrypoints:
  - src/routes/billing.ts
data_objects:
  - invoice
evidence_refs:
  - src/routes/billing.ts
notes: Public-safe summary only.
```

Rules:

- `business_id` is lowercase, stable, and repository-local.
- `status` is one of `active`, `deprecated`, `prototype`, `external_only`, or `unknown`.
- `document_status` is one of `missing`, `draft`, `review`, `approved`, `low_confidence`, `stale`, `blocked`, or `not_applicable`.
- `criticality` is one of `critical`, `high`, `medium`, or `low`.
- Human names, customer names, private hosts, account numbers, and raw logs are not allowed.

### `doc_gap_report`

Purpose: make missing or weak documentation visible before release decisions.

Each `gap_items` entry includes:

- `business_id` or `global_scope`
- `missing_doc_type`
- `document_status`
- `impact`
- `evidence_refs`
- `recommended_action`
- `owner_role`

Allowed `recommended_action` values:

- `generate_domain_docs`
- `review_evidence`
- `mark_not_applicable`
- `refresh_stale_docs`
- `manual_confirm`

### `domain_business_spec`

Purpose: describe one business domain from the product and operations view.

Required sections:

- business_id
- scope
- actors
- business flow
- state model
- permissions
- inputs_outputs
- edge_cases
- evidence_refs
- assumptions
- missing_evidence

### `domain_technical_design`

Purpose: describe implementation evidence for the same `business_id`.

Required sections:

- business_id
- code locations
- interfaces
- table structure
- state and cache behavior
- integration dependencies
- test points
- operational risks
- evidence_refs
- assumptions
- missing_evidence

## Execution And Drift Records

### `task_execution_record`

Purpose: record what one task changed and how it was verified.

Required fields:

```yaml
task_id: WHA-000
issue_id: WHA-000
pr_url: null
commit_sha: null
changed_files: []
verification: []
risk_items: []
follow_up_items: []
completed_at: null
public_safety:
  reviewed: true
```

Use routable issue keys when available. If there is no PR or commit yet, use `null` rather than placeholder private URLs.

### `version_iteration_record`

Purpose: summarize a release candidate or iteration from multiple task records.

Required fields:

- version_id
- objective
- included_tasks
- changed_capabilities
- verification_summary
- release_channel
- release_gate
- rollback_notes
- risks
- follow_up_items

For pre-release work, `release_channel` remains `private_beta` until the release gate is explicitly passed.

### `affected_docs`

Purpose: classify document drift after code, config, API, schema, cache, permission, or business flow changes.

Each item includes:

```yaml
doc_path: .axis/docs/projects/{project_slug}/domains/billing/domain_technical_design.md
business_id: billing
change_type: code
drift_status: needs_revision
impact: high
evidence_refs:
  - src/routes/billing.ts
recommended_action: refresh_stale_docs
```

Allowed `change_type` values:

- `code`
- `api`
- `schema`
- `cache`
- `permission`
- `business_flow`
- `config`
- `docs`

Allowed `drift_status` values:

- `unchanged`
- `needs_revision`
- `stale`
- `missing`
- `conflict`
- `not_applicable`

## Public-Safe Evidence Rules

The shorthand rule is: do not invent.

- Prefer repository paths, line-oriented summaries, and sanitized command names.
- Do not invent architecture, business flow, permissions, table structure, or ownership when evidence is not present.
- Do not copy raw logs, stack traces with account data, customer identifiers, private hostnames, tokens, cookies, keys, or connection strings.
- Do not include side-effecting mention links in committed protocol examples.
- Record confidence and missing evidence instead of converting unknowns into approved facts.

## Release Readiness Use

A private_beta release candidate that includes the project knowledge skills is release-ready only when:

- this protocol source is committed under `docs/`;
- the repository has a public-safe `.axis/config.yml`;
- config validation passes from the PR checkout;
- local-only and dry-run outbox package validation pass without upload;
- `axis-project-knowledge-bootstrap`, `axis-business-domain-doc`, and `axis-doc-drift-capture` validators pass;
- full repository tests and diff checks pass.
