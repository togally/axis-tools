# Axis v0.2 Default and Conversational Project Configuration

Date: 2026-07-10
Status: Approved design

## Objective

Expire the Axis v0.1 package contract, make v0.2 the only active and default
contract, and let `axis-doc-project-init` configure a user-selected repository
through a field-by-field conversation.

The configuration flow must reuse existing values when possible, let the user
switch organizations and OSS profiles without deleting old registry entries,
and never collect secret values in conversation or committed files.

## Decisions

- v0.1 is expired, not merely deprecated. Existing v0.1 configuration may be
  inspected for migration, but it cannot pass validation, create captures, or
  publish packages.
- New projects, manifests, metadata, package paths, protocol declarations, and
  checked-in examples use v0.2.
- The Skill owns the conversation. The CLI owns inspection, migration,
  validation, and writes.
- Existing values are shown one field at a time. A stored value is proposed as
  the default, but the user must confirm or change it.
- Switching the selected organization or OSS profile preserves all unselected
  registry entries.
- Credentials remain outside Axis files and the conversation. The Skill
  recommends environment variable names, checks whether the variables exist,
  prints placeholder shell commands for missing variables, waits for the user,
  and rechecks before applying configuration.
- Every new protocol version must ship a machine-readable mapping from the
  immediately preceding version. Older configurations migrate through the
  complete adjacent-version chain before the latest-version fields are shown
  to the user.

## Scope

This change covers:

- contract lifecycle and v0.1 rejection;
- v0.2 defaults in the CLI and this repository;
- adjacent-version migration definitions and the migration engine;
- deterministic project inspection and apply commands;
- safe organization registry upserts;
- conversational behavior in `axis-doc-project-init`;
- documentation, governance, and tests.

It does not add a credential store, execute shell commands containing user
secrets, delete historical registry records, or publish an OSS package as part
of project initialization.

## Architecture

### Skill layer

`axis-doc-project-init` is the conversational orchestrator. It:

1. Obtains the target repository path or confirms a path already provided by
   the user.
2. Runs the read-only inspection command.
3. Presents every latest-version field separately with its current value,
   mapped value, recommendation, and provenance.
4. Lets the user keep or replace each value, including the organization and OSS
   profile selection.
5. Recommends environment variable names and confirms those names without
   asking for the variable values.
6. Checks the required variables. If any are absent, it prepares shell commands
   with user-fillable placeholders and explains that checking and apply must run
   in that same shell process.
7. Shows a complete final summary and requires explicit approval.
8. Writes an answers file containing configuration values but no credentials.
9. If the Agent process already has the variables, it invokes apply. Otherwise,
   it gives the user one shell block that exports the values, checks them, and
   invokes apply without exposing them to the conversation.
10. Reads the generated files and reports success only after post-write
    validation passes.

The Skill must not collapse existing configuration into a single bulk
confirmation. Existing values are still presented one by one so the user can
switch configuration deliberately.

### CLI layer

The CLI exposes a two-phase contract:

```bash
axis project-init --repo <path> --inspect --json \
  [--registry-path <relative-path>] \
  [--organization-id <id>] \
  [--oss-profile <name>]
axis project-init --repo <path> --recover
axis project-init --repo <path> --answers-file <path> --apply
```

`--inspect` is read-only. It parses existing Axis files, resolves the migration
chain to the latest protocol, computes field provenance and recommendations,
hashes the files that would be changed, and reports environment variable
presence without exposing values.

`--recover` is the only recovery mode and is explicitly mutating. It resolves a
transaction journal by restoring the all-old state for an uncommitted
transaction or removing artifacts for a committed transaction. `--inspect`
never performs recovery; it reports `recovery_required` and stops when a
journal exists.

`--apply` validates the answers document, verifies that inspected files have
not changed, rechecks required environment variables, renders both target YAML
documents, validates the rendered result, and performs a guarded write. It then
runs the same effective validation used by `axis validate-config`.

The old direct form using only `--project-slug`, `--display-name`, and `--force`
is expired because it cannot express a complete v0.2 configuration. It fails
with guidance to use inspect and an answers file. The only write path is
`--answers-file ... --apply`.

Project initialization continues to add `.axis/config.local.yml` and
`.axis/outbox/` to `.gitignore`. Main config, optional local config, selected
target registry, and `.gitignore` form one inspected and transactionally
updated target set.

### Inspection and answers contracts

`--inspect --json` returns `axis.project_init_inspection` schema version 1 with
these required top-level values:

- absolute `repo` path;
- nullable `source_contract_version` and fixed `latest_contract_version`;
- `selectors`, containing the candidate registry path, organization ID, and OSS
  profile name used for this inspection;
- `files`, containing main config, local config, target registry, source registry
  when different, and gitignore entries with `role`, `path`,
  `state: present | absent`, and `sha256`, which is null only when absent;
- ordered `migration_chain` edges with mapping file identifiers;
- ordered `fields`, one per latest-version conversational field;
- `environment`, containing variable field, recommended or confirmed name,
  required status, and presence boolean.

Each `fields` entry contains `key`, human label, required status, current value
when present, mapped value when available, recommendation when available,
stable sorted options when applicable, resolution, and an ordered provenance
list. It never contains a credential value.

The answers file uses `axis.project_init_answers` schema version 1 and contains:

- the exact repository path and latest contract version from inspection;
- the exact selector tuple from the final inspection;
- the exact `files` fingerprints from inspection, including absent states;
- exactly one decision for every inspected field, preserving field order;
- for each decision, `key`, final `value`, and
  `decision: keep | accept_mapping | accept_recommendation | change`;
- `final_confirmation: true`, written only after the user approves the complete
  summary.

The answers schema rejects unknown fields, missing decisions, duplicate keys,
secret-value properties, a repository mismatch, and any non-v0.2 target. The
two contracts are defined by JSON Schemas so the Skill and CLI share one
versioned interface.

Registry path, organization ID, and OSS profile name are hierarchical selector
fields. The Skill confirms them in that order. Changing a selector causes a new
read-only inspection with the chosen selector values and invalidates every
downstream decision:

- changing registry path invalidates organization, profile, and all registry
  field decisions;
- changing organization invalidates profile and all organization/profile field
  decisions;
- changing profile invalidates all profile and environment-name decisions.

The final answers file may only use fields emitted by the final selector-bound
inspection. Apply verifies each decision against that inspection's selector
context, so values from one organization or profile cannot be applied to
another. The selected target registry always has a present or absent
fingerprint, even when it differs from the registry referenced by the source
config. A source registry that is not the selected target is read-only and is
never overwritten.

The following inspection and answers examples are abridged; repeated file and
field entries are omitted, while the JSON Schemas require their complete sets.

Representative inspection shape:

```json
{
  "schema": "axis.project_init_inspection",
  "schema_version": 1,
  "repo": "/workspace/demo",
  "source_contract_version": "0.1",
  "latest_contract_version": "0.2",
  "selectors": {
    "registry_path": ".axis/organizations.yml",
    "organization_id": "org_demo",
    "oss_profile": "private_beta_main"
  },
  "files": [
    {
      "role": "target_registry",
      "path": ".axis/organizations.yml",
      "state": "absent",
      "sha256": null
    }
  ],
  "migration_chain": [
    { "from": "0.1", "to": "0.2", "mapping": "0.1-to-0.2.yml" }
  ],
  "fields": [
    {
      "key": "project.slug",
      "required": true,
      "mapped_value": "demo",
      "resolution": "mapped",

      "field": "access_key_id_env",

```

Representative answers shape:

```json
  "schema_version": 1,
  "repo": "/workspace/demo",

    "organization_id": "org_demo",

  "files": [
    {
      "role": "target_registry",

      "state": "absent",
      "sha256": null
    }
  ],
  "decisions": [
    {
      "key": "project.slug",
      "value": "demo",
      "decision": "accept_mapping"
    }

}
```

### Migration layer

Migration definitions live under:

```text
protocols/migrations/<from>-to-<to>.yml
```

They are validated by `schemas/protocol-migration.schema.json`. A definition
must connect exactly one version to its immediate successor and may contain
these operations:

- `copy`: copy a source field to a target field;
- `set`: assign a fixed target value or protocol default;
- `prompt`: mark a target field as unresolved and attach prompt metadata and a
  recommendation source when available;
- `drop`: explicitly remove an old field and record the reason.

Mappings operate on a normalized configuration draft rather than directly on
YAML array indexes. The draft has stable sections for protocol, project,
package, release, organization, OSS profile, and environment variable names.
The v0.2 renderer converts the confirmed draft into `.axis/config.yml` and the
selected entries in `.axis/organizations.yml`.

Each migrated field carries provenance:

```json
{
  "target": "oss_profile.bucket",
  "value": "example-bucket",
  "source_version": "0.1",
  "source": "oss.bucket",
  "resolution": "mapped"
}
```

`resolution` is one of `stored`, `mapped`, `recommended`, or `user_modified`.
Unresolved `prompt` fields are accumulated while other fields continue through
the version chain. The Skill asks for unresolved values only after the draft
reaches the latest version.

The migration engine rejects missing links, non-adjacent links, duplicate
links, cycles, invalid mapping files, conflicting writes to the same target,
and a chain that does not terminate at the current version. It never guesses a
cross-version conversion.

## v0.1 to v0.2 Mapping

The first mapping preserves directly compatible project, package, release, and
OSS values. It changes the contract version to `0.2`, maps the old inline OSS
fields into the selected registry profile, and prompts for fields that v0.1 did
not contain:

- organization ID, slug, and display name;
- organization status when no stored organization exists;
- registry path when no registry exists;
- selected OSS profile name.

Existing v0.2 registry data participates in recommendation selection. The
matching order is deterministic:

1. An existing v0.2 config reference wins by exact organization ID and profile
   name.
2. Migrated v0.1 OSS data matches a profile only when provider, bucket, prefix,
   and all configured environment variable names are equal.
3. One exact profile match is recommended. Multiple exact matches are returned
   as options sorted by organization ID and profile name, with no automatic
   selection. No exact match proposes a new entry.

For a new entry, organization ID is recommended as `org_<project-slug>`,
organization slug and display name reuse the confirmed project values, status
is `active`, and profile name is `private_beta_main`. Identifier normalization
lowercases ASCII, converts unsupported runs to one separator, and trims edge
separators. A collision receives the first available stable numeric suffix,
starting at `_2`. Every recommendation still requires field-level user
confirmation.

## Latest v0.2 Configuration Model

The field-by-field conversation covers:

- target repository path;
- project slug and display name;
- package outbox directory;
- release channel and gate;
- organization registry path;
- organization ID, slug, display name, and status;
- OSS profile name, provider, bucket, and prefix;
- endpoint, region, AccessKey ID, and AccessKey Secret environment variable
  names;
- optional Security Token environment variable name.

`contract_version` is fixed to `0.2` and is displayed as a protocol decision,
not offered as a selectable field. The current supported provider remains
`aliyun-oss`.

## Registry Update Rules

The selected organization is matched by ID and the selected OSS profile by
name. Their selector tuple comes from the final inspection, and all dependent
field decisions are scoped to that tuple. The renderer uses structured YAML
parsing and serialization; it does not perform string replacement.

- A matching entry is updated only with fields the user confirmed as changed.
- Other organization fields and unknown extension keys are preserved.
- Unselected organizations, OSS profiles, products, and projects are preserved.
- A newly configured project is upserted under the selected organization.
- Switching selection changes `.axis/config.yml` references but does not delete
  the previous selection.
- Duplicate project slugs within one organization remain invalid.
- Credentials and private endpoint values are never written; only environment
  variable names are stored.

## Local Configuration Migration

`.axis/config.local.yml` is local-only but participates in effective publish
configuration, so it is inspected, fingerprinted, migrated, and included in the
same transaction when present. Initialization does not create it when absent.

The v0.1-to-v0.2 local mapping:

- sets an existing `contract_version` to `0.2`;
- preserves `local.dry_run`, `local.outbox_dir`, redaction settings, and unknown
  local extension keys;
- preserves and individually confirms OSS environment variable name overrides;
- drops local provider, bucket, prefix, or credential-like value fields with an
  explicit migration record because v0.2 resolves the target from the selected
  registry profile and never stores credential values.

If an unsupported or credential-like local field is present, inspection marks
it for removal and the Skill shows that decision before final confirmation.
Apply fails rather than silently dropping it when no matching `drop` operation
exists in the adjacent-version mapping.

Environment presence checks use the final effective variable name for each
field: a confirmed local override wins over the selected registry profile name.
Every stored local override is shown separately. The user may keep, change, or
clear it; clearing an override falls back to the registry profile.

## Environment Variable Gate

Inspection returns each variable name and a boolean `present` value. It must
not return environment variable contents.

The required variables are those named by `endpoint_env`, `region_env`,
`access_key_id_env`, and `access_key_secret_env`. `security_token_env` is
checked when the user elects to configure it.

For missing variables, the Skill prints a single shell block such as:

```bash
export ALIYUN_OSS_ACCESS_KEY_ID='<fill-in-locally>'
export ALIYUN_OSS_ACCESS_KEY_SECRET='<fill-in-locally>'
test -n "$ALIYUN_OSS_ACCESS_KEY_ID" && \
  test -n "$ALIYUN_OSS_ACCESS_KEY_SECRET" && \
  axis project-init --repo '<path>' --answers-file '<path>' --apply
```

The user fills and runs the block locally only after approving the final
summary. Checks and apply run in the same shell process, avoiding the false
assumption that an Agent process inherits exports from another terminal. The
Skill then verifies the generated files and validation output. Apply is blocked
until the required variables are present. Neither stdout, stderr, generated
JSON, nor the final summary may contain their values.

## Safe Apply and Concurrency

Inspection returns SHA-256 fingerprints and explicit absent states for main
config, local config, the selected target registry, and gitignore. A different
source registry may be included as read-only context. The answers document
carries those values. Apply rejects stale answers if a present target changed,
an absent target appeared, or a present target disappeared after inspection.

Before replacing files, apply:

1. validates the answers document;
2. builds the complete v0.2 config and registry in memory;
3. serializes and reparses both YAML documents;
4. resolves the generated config against the generated registry;
5. writes temporary files in the destination directories;
6. records original and target hashes in a credential-free transaction journal;
7. replaces main config, optional local config, registry, and gitignore with
   rollback protection;
8. reruns effective config validation from disk;
9. marks the transaction committed and removes journal and backup artifacts.

Caught replacement or post-write validation failures restore all original
bytes and remove temporary files. After abrupt process or host interruption,
inspect and apply stop with `recovery_required` and do not mutate files. The
user or Skill must explicitly run `--recover`; an uncommitted journal then
restores the all-old state, while a fully committed journal finishes cleanup.
This recovery rule prevents a mixed main-config/local-config/registry/gitignore
state from becoming the next accepted baseline without violating inspect's
read-only contract.

## v0.1 Expiration Behavior

The parser retains enough knowledge of v0.1 to inspect and migrate it. All
normal configuration consumers reject it with a stable error that states:

- v0.1 is expired;
- v0.2 is the current version;
- the repository can be migrated with `axis-doc-project-init` or
  `axis project-init --repo <path> --inspect --json`.

The rejection applies to `validate-config`, `coding-capture`, `test-report`, and
`oss-publish`. No v0.1 outbox package is newly generated or published.
Historical v0.1 documents remain available and are visibly marked expired.

## Repository Defaults and Documentation

- `defaultConfigYaml` is replaced by the v0.2 answers renderer.
- `protocolVersions` uses `0.2` for document, workflow, experience, and agent
  execution protocols.
- Package and manifest defaults use the v0.2 organization-scoped path.
- This repository's `.axis/config.yml` and public-safe organization registry
  use v0.2 example data.
- README command examples and the bilingual Skill catalog describe v0.2.
- `governance/DEPRECATION.md` defines the adjacent mapping requirement for all
  future protocol releases.
- v0.1 documents are retained as historical references and marked expired.

## Error Handling

No write occurs when:

- the repository path is absent or is not a directory;
- config or registry YAML is malformed;
- the migration chain is missing, invalid, or conflicting;
- the answers document is invalid or incomplete;
- required environment variables are missing;
- inspection fingerprints are stale;
- the generated v0.2 config or registry fails validation.

Errors identify the failing field or migration edge and give the next safe
action. Errors never include credential values.

## Verification Strategy

Implementation follows test-driven development. Focused tests are added and
observed failing before production changes.

CLI and migration coverage includes:

- default initialization generates only v0.2 config and registry data;
- every normal command rejects v0.1 with migration guidance;
- the v0.1-to-v0.2 mapping preserves compatible fields and records provenance;
- fixture mappings prove a multi-hop old-to-latest chain;
- missing links, conflicting targets, and invalid mappings fail without writes;
- registry upsert preserves unselected and unknown data;
- selector changes invalidate and re-inspect all dependent field decisions;
- v0.1 local config maps effective environment-name overrides to v0.2;
- stale fingerprints reject apply;
- missing environment variables block apply without exposing values;
- failed target-set replacement restores original bytes;
- absent-file fingerprints and transaction-journal recovery are deterministic;
- generated manifests and paths use v0.2.

Skill coverage includes baseline and post-change conversation scenarios that
verify:

- a target project path is requested when absent;
- every stored field is shown separately for confirmation;
- organization and profile switching preserves old entries;
- environment variable names are recommended, not secret values requested;
- missing variables produce placeholder shell commands and pause the flow;
- apply occurs only after the final summary is explicitly approved.

Repository verification ends with the focused test files, `npm test`, schema
validation, packaged Skill validation, local Codex Skill refresh, and an
end-to-end temporary-repository initialization and v0.1 migration exercise.
Golden fixtures cover an empty repository, v0.1 migration, v0.1 local-config
migration, multiple exact registry matches, an absent file appearing after
inspection, and interrupted replacement recovery. Implementation sequencing
makes migration inspection and apply operational before normal commands begin
rejecting v0.1.

## Success Criteria

- A new project configured by the Skill ends with a valid v0.2 project config
  and organization registry.
- A v0.1 project cannot continue normal Axis operations and can be migrated
  through the declared adjacent mapping.
- A future multi-version project can migrate through all available adjacent
  mappings without a hand-written cross-version converter.
- The user sees and confirms every final field, including values brought
  forward from stored data.
- Switching configuration never silently deletes stored organizations or OSS
  profiles.
- Existing local-only behavior and effective environment-name overrides survive
  migration unless the user explicitly changes or clears them.
- Configuration completion is not reported until required environment
  variables exist and final validation passes.
- No credential value is written or printed.
