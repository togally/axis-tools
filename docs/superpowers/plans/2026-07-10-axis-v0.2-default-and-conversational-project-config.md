# Axis v0.2 Default and Conversational Project Configuration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Expire Axis v0.1, make v0.2 the only active/default package contract, and provide a deterministic CLI that the `axis-project-init` Skill can drive through field-by-field conversational configuration and adjacent-version migration.

**Architecture:** Keep command routing and existing package behavior in `src/cli.ts`, but move project initialization into focused modules for migration, inspection, rendering, and transactional apply/recovery. Versioned JSON Schemas define the Skill/CLI boundary; adjacent YAML mappings produce a normalized draft with provenance before selector-bound answers are applied.

**Tech Stack:** TypeScript ES modules, Node.js 22 APIs, `yaml` document API, Ajv JSON Schema validation, Node assertion-based integration tests, packaged Codex Skills.

- [ ] **Step 3: Implement transaction primitives**

The journal records transaction state, target paths, original/target hashes,
original absent states, and backup/temp paths, never file contents or
environment values. Its state machine is:

```text
no journal -> prepared -> replacing -> committed -> no journal
```

Create and fsync backup/new files, then fsync every directory containing those
entries, before atomically writing `prepared`. Only after that durability barrier
may the journal temp file be renamed to `prepared` and its directory fsynced.
Write all later journal updates through the same temp-file + rename + directory
fsync sequence.
During `replacing`, record the replacement index for diagnostics, but recovery
must classify actual target hashes against original/new hashes instead of
trusting the index alone. An uncommitted journal always restores all-old,
including deleting targets that were originally absent. A committed journal
requires all-new hashes and only finishes cleanup; any third hash stops with a
manual-remediation error rather than guessing.

After every target rename, fsync that target's destination directory before
advancing the journal. After rollback restores or deletes targets, fsync every
affected destination directory before removing the journal. Write `committed`
only after all target directories and post-write validation are durable. During
committed cleanup, fsync directories after deleting backup/temp artifacts and
before removing the journal; then fsync the journal directory again. Fault
tests assert this ordering, not only final bytes.

Use injected filesystem/fault hooks in tests to simulate process termination at
every transition without production-only environment flags. Implement:

```ts
export async function applyProjectInit(options: ApplyOptions): Promise<ApplyResult>;
export async function recoverProjectInit(repo: string): Promise<RecoveryResult>;
```

Apply orchestration must be explicit:

1. Read the answers file.
2. Run selector-bound inspection using the registry path, organization ID, and
   profile embedded in answers.
3. Compare the new inspection fingerprints with the answers fingerprints and
   pass that inspection to `validateAnswers`.
4. Validate effective environment names.
5. Render and reparse the complete target set.
6. Invoke an in-memory effective-config callback with parsed rendered main
   config, target registry, and local overrides before any replacement.
7. Execute the journaled replacement.
8. Invoke the existing disk-reading effective validator after replacement.
9. Mark committed and clean up, or roll back on caught errors.

Refactor `resolveAxisConfig` options to accept a selector-bound registry
override for pre-write validation while preserving its normal disk loader for
post-write validation. This prevents the current registry on disk from being
mistaken for the rendered target registry.
