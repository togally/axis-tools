# Axis Doc-as-Code Protocols v0.1 (Expired)

> This document is retained for historical reference and migration input only. Axis v0.1 is expired; new packages and workflows use v0.2.

## Design Conclusion

Axis doc-as-code v0.1 defines four logical protocols above the WHA-9 package contract: Document Protocol, Workflow Protocol, Experience Protocol, and Agent Execution Protocol. These protocols define how project knowledge is authored, approved, versioned, executed, reported, and reused. They do not turn `axis-ops-oss-publish` into a workflow engine, and they do not change the WHA-9 package rule that a v0.1 OSS package contains exactly `manifest.json`, `metadata.json`, `report.md`, and `experience.md`.

The v0.1 compatibility model is:

- source documents live in public-safe repository paths under `.axis/`;
- approved documents are immutable for execution; corrections create a new revision that supersedes the previous revision;
- agents execute only an approved Agent Execution Pack that references approved documents by ID, version, path, and checksum;
- execution produces an Execution Report and zero or more Experience Card candidates;
- existing tools and packaged skills are governed through a lightweight Tool / Skill Catalog that maps capabilities to document inputs, report outputs, and experience scopes;
- experience candidates must pass dedupe, quality, lifecycle, and public-safety gates before they are loadable by skills;
- blocked workflows and partial executions recover through explicit retry/resume metadata, not by mutating approved packs in place;
- code-map drift is handled through execution-report deltas and new approved document revisions, not silent edits to an approved project brief;
- `manifest.json` and `metadata.json` may carry optional protocol indexes, but OSS publisher only validates and uploads package files.

## Business Design

### Scope and Boundaries

The four protocols own doc-as-code semantics:

| Area | Owns | Does Not Own |
| --- | --- | --- |
| Document Protocol | Document identity, type, metadata, state, version, owner, storage path, public-safety classification, and human-readable code map fields. It also owns code-map freshness metadata and code-map delta review rules. | OSS upload, package checksums, credential handling, search service, approval authority implementation, automatic code analysis service. |
| Workflow Protocol | Dynamic workflow templates, workflow run records, blocked reasons, checkpoints, and retry/resume policies for project creation, import, iteration, hotfix, test/benchmark, release, and retrospective flows. | Runtime scheduling, agent queueing, permission system, UI workflow builder, automatic retry executor. |
| Experience Protocol | Experience scope, storage shape, promotion path, conflict rules, cold-start behavior, dedupe/cluster keys, lifecycle/TTL, and skill loading strategy. | Skill installation, model prompt internals, central knowledge service, automatic knowledge graph clustering service. |
| Agent Execution Protocol | Minimum executable fields for handing approved work to an agent, expected outputs, execution report shape, required experience capture, public-safety validation evidence, retry context, and code-map delta reporting. | Agent identity provider, sandbox policy, issue tracker workflow, deployment permission, runtime orchestration. |
| `manifest.json` | Package identity, file list, checksums, publish location, and optional protocol reference indexes. | Approval decisions, workflow state transitions, execution planning. |
| `axis-ops-oss-publish` | Read config, validate package files, upload objects, upload `manifest.json` last. | Creating or changing protocol documents, approving work, executing workflows, promoting experience. |

### Tool / Skill Catalog

Tool / Skill Catalog is a lightweight executable-capability directory that connects Document Protocol, Experience Protocol, and Agent Execution Protocol. It is not a fifth protocol, not a runtime, not a permission system, and not a tool scheduler. v0.1 uses it to answer three questions:

- which tool or skill can consume which approved document types;
- which experience scopes a tool or skill may load;
- which report or experience candidate types a tool or skill may produce.

Catalog families group existing axis-tools capabilities instead of listing every tool as a separate protocol surface:

| `canonical_family` | Packaged Skills / Scripts | Typical Inputs | Typical Outputs |
| --- | --- | --- | --- |
| `document_design` | `axis-doc-development`, `axis-doc-tech-design`, `axis-doc-db-design` | `project_brief`, `version_plan`, `decision_record` | `decision_record`, `agent_execution_pack`, `execution_report`, `experience_card` candidate |
| `fix_optimize` | `axis-code-bugfix`, `axis-code-arch-optimize`, `axis-code-api-performance-tuning` | `agent_execution_pack`, `project_brief`, `version_plan`, code-map refs | `execution_report`, `code_map_delta`, `experience_card` candidate |
| `test_verify_benchmark` | `axis-test-tdd`, `axis-test-side-effects`, `axis-test-benchmark` | `agent_execution_pack`, test plan, benchmark plan | `test_report`, `benchmark_report`, `execution_report`, `experience_card` candidate |
| `skill_governance` | `axis-tools-skill-create`, `axis-tools-prompt-create`, `axis-tools-skill-update`, `axis-skill-create.mjs`, `axis-skill-update.mjs`, `axis-skill-deposit.mjs`, `install-axis-tools.sh` | `decision_record`, skill source docs, catalog metadata | `execution_report`, skill metadata update, `experience_card` candidate |
| `domain_specialty` | `axis-ops-ali-dashboard` | domain-specific dashboard request and public-safe references | `execution_report`, domain artifact, `experience_card` candidate |

Catalog governance fields:

| Field | Rule |
| --- | --- |
| `tool_id` | Stable ID for a script, CLI entry, or non-skill executable capability. |
| `skill_id` | Stable packaged skill ID when the capability is a skill. |
| `canonical_family` | One of the grouped families above. |
| `capability_tags` | Public-safe tags used for matching tools to execution packs and experience cards. |
| `input_document_types` | Document types the tool may consume. |
| `output_document_types` | Document/report types the tool may produce. |
| `experience_consumes_scopes` | Allowed scopes from `task`, `version`, `project`, `team`, `domain`, `global`. |
| `experience_candidate_outputs` | Candidate scopes the tool may write after execution. |
| `public_safety` | Required public-safety validation rules for tool inputs and outputs. |
| `status` | `active`, `review`, `deprecated`, `replaced`, or `archived`. |
| `owner.role` | Governance owner role, not a permission grant. |
| `deprecated` | Boolean marker for capabilities that should no longer be selected by default. |
| `replaced_by` | Replacement `tool_id` or `skill_id`, required when `status: replaced`. |

Catalog rules:

- An execution pack may reference catalog entries through `tool_refs` or `skill_refs`.
- Deprecated tools are excluded from default selection unless the execution pack explicitly allows them.
- A `replaced` entry must set `replaced_by`; consumers should resolve to the replacement unless the pack pins the old tool for compatibility.
- Catalog matching is advisory. It tells the agent which capability and experience scopes are allowed; it does not execute or authorize the tool.

### Document Protocol

Document Protocol makes every durable project artifact a typed, versioned, public-safe document. Humans use it to understand the project, workflow, decisions, code map, execution history, and reusable lessons. Agents use it only through approved references in an execution pack.

Required v0.1 document types:

| Type | Purpose | Default Path |
| --- | --- | --- |
| `project_brief` | Project purpose, boundaries, owners, glossary, and code map. | `.axis/docs/projects/{project_slug}/project.brief.yaml` |
| `version_plan` | Version objective, scope, milestones, acceptance criteria, and linked decisions. | `.axis/docs/projects/{project_slug}/versions/{version_id}/plan.yaml` |
| `decision_record` | Approved technical or product decision with consequences. | `.axis/docs/projects/{project_slug}/decisions/{decision_id}.yaml` |
| `agent_execution_pack` | Approved executable instruction package for one agent task. | `.axis/docs/projects/{project_slug}/agents/{pack_id}.execution-pack.yaml` |
| `execution_report` | Result report from an agent execution pack. | `.axis/docs/projects/{project_slug}/reports/{run_id}.execution-report.yaml` |
| `test_report` | Test result report with command, evidence, and limitations. | `.axis/docs/projects/{project_slug}/reports/{run_id}.test-report.yaml` |
| `benchmark_report` | Benchmark result report with capacity interpretation and limits. | `.axis/docs/projects/{project_slug}/reports/{run_id}.benchmark-report.yaml` |
| `experience_card` | Reusable experience promoted through Experience Protocol. | `.axis/experience/{scope}/{experience_id}.yaml` |

Document states:

| State | Meaning | Executable |
| --- | --- | --- |
| `draft` | Authoring in progress. | no |
| `review` | Ready for human review. | no |
| `approved` | Frozen for execution or reuse. | yes, only when referenced by an approved pack |
| `executing` | An approved pack is being executed. | no new execution starts from this state |
| `completed` | Execution/reporting is complete. | no |
| `superseded` | Replaced by a newer approved revision. | no |
| `archived` | Retained for history only. | no |
| `rejected` | Reviewed and rejected. | no |

Approved documents are immutable for v0.1 execution. A correction creates a new `revision`, writes a new checksum, and sets `supersedes` to the previous document revision.

Code-map synchronization fields:

| Field | Rule |
| --- | --- |
| `code_map.status` | `verified`, `stale`, or `delta_pending`. |
| `code_map.last_verified_at` | UTC timestamp for the last approved verification. |
| `code_map.verified_by.role` | Human or agent role that performed the verification; this is not a permission grant. |
| `code_map.update_policy` | Must be `report_delta_then_new_revision` for v0.1. |
| `execution_report.code_map_delta` | Required when an execution changes mapped directories, entrypoints, contracts, or module responsibilities. |

Code-map drift rules:

- Agents must not silently mutate an approved `project_brief`.
- If code structure changes, the execution report must include a `code_map_delta` with `added`, `changed`, `moved`, and `removed` entries.
- If a pack explicitly allows documentation edits, the agent may write a new `project_brief` revision with `status: review`; the old approved revision remains the executable source until the new revision is approved.
- If code changes affect mapped paths and no `code_map_delta` is produced, the execution report must be `partial` or `failed`, and the workflow run remains `blocked` with `blocked_reason: code_map_delta_missing`.

### Workflow Protocol

Workflow Protocol defines reusable templates and run records. It tells humans and agents which documents must exist, which approvals are required, what outputs are expected, and which pack can be executed next. It is not an execution engine.

Required v0.1 workflow templates:

- `project_create`;
- `project_import`;
- `version_iteration`;
- `hotfix`;
- `test_benchmark`;
- `release_retrospective`.

Workflow states:

| State | Meaning |
| --- | --- |
| `draft` | Template or run is being authored. |
| `approved` | Template or run is approved for use. |
| `running` | A workflow run has active steps. |
| `blocked` | A required decision, document, or report is missing. |
| `retrying` | A blocked step is being retried with the same approved pack and unchanged inputs. |
| `resume_pending` | A blocked step needs a new approved pack or human decision before it can resume. |
| `completed` | All required steps and reports are complete. |
| `cancelled` | The workflow run was intentionally stopped. |

Example project creation workflow template:

```yaml
schema: axis.workflow
schema_version: "0.1"
workflow_id: workflow_project_create_v001
workflow_type: project_create
title: New Project Creation
status: approved
storage:
  path: .axis/workflows/templates/project-create.workflow.yaml
owner:
  role: project_owner
triggers:
  - manual_project_start
required_inputs:
  - project_slug
  - project_display_name
  - initial_scope
steps:
  - step_id: create_project_brief
    title: Create project brief and code-map placeholder
    required_documents:
      - doc_type: project_brief
        status: approved
    expected_outputs:
      - .axis/docs/projects/{project_slug}/project.brief.yaml
  - step_id: create_initial_version_plan
    title: Create initial version plan
    depends_on:
      - create_project_brief
    required_documents:
      - doc_type: version_plan
        status: approved
    expected_outputs:
      - .axis/docs/projects/{project_slug}/versions/v0.1/plan.yaml
  - step_id: approve_execution_pack
    title: Approve the first agent execution pack
    depends_on:
      - create_initial_version_plan
    required_documents:
      - doc_type: agent_execution_pack
        status: approved
    expected_outputs:
      - .axis/docs/projects/{project_slug}/agents/{pack_id}.execution-pack.yaml
completion:
  required_terminal_documents:
    - doc_type: execution_report
      status: completed
    - doc_type: experience_card
      status: review
recovery:
  retry_policy:
    max_attempts_per_step: 2
    retryable_failure_types:
      - network_timeout
      - dependency_unavailable
  resume_policy:
    same_pack_retry_allowed_when:
      - approved_document_refs_unchanged
      - scope_unchanged
      - failure_type_retryable
    new_pack_required_when:
      - scope_changed
      - approved_document_changed
      - acceptance_criteria_changed
```

Blocked recovery fields for workflow runs:

| Field | Rule |
| --- | --- |
| `blocked_reason` | Machine-readable reason such as `missing_required_output`, `external_dependency_unavailable`, `partial_execution`, `public_safety_failed`, or `code_map_delta_missing`. |
| `blocked_at` | UTC timestamp when the run entered `blocked`. |
| `blocked_step_id` | Step that cannot continue. |
| `last_successful_step_id` | Last completed step, if any. |
| `checkpoint_ref` | Public-safe reference to the execution report, package, or document that can be used to resume. |
| `retry_policy.max_attempts_per_step` | Maximum same-pack retry count. |
| `retry_policy.retryable_failure_types` | Failure types that may retry without a new pack. |
| `resume_policy.same_pack_retry_allowed_when` | Conditions for retrying the same immutable approved pack with a new `run_id`. |
| `resume_policy.new_pack_required_when` | Conditions that force a new approved execution pack. |

Recovery rules:

- The approved execution pack is immutable. A retry creates a new execution `run_id` and links to the previous report through `retry_of_run_id`.
- A same-pack retry is allowed only when scope, approved document refs, checksums, and acceptance criteria are unchanged and the failure type is retryable.
- Any change to scope, inputs, approved documents, acceptance criteria, or allowed actions requires a new approved execution pack.
- Workflow Protocol records `blocked`, `retrying`, and `resume_pending` state. It does not schedule retries or enqueue agents by itself.

### Experience Protocol

Experience Protocol defines reusable knowledge as scoped cards. Only approved cards are loadable by skills by default. Draft or review cards can be inspected by humans, but they must not silently affect agent behavior.

Experience scopes:

| Scope | Use | Storage |
| --- | --- | --- |
| `global` | Cross-domain public-safe practice. | `.axis/experience/global/{experience_id}.yaml` |
| `domain` | Reusable practice for one technical or business domain. | `.axis/experience/domain/{domain_slug}/{experience_id}.yaml` |
| `team` | Team convention or operating preference. | `.axis/experience/team/{team_slug}/{experience_id}.yaml` |
| `project` | Project-specific architecture, constraints, or code-map learning. | `.axis/experience/project/{project_slug}/{experience_id}.yaml` |
| `version` | Version-specific lesson or release constraint. | `.axis/experience/project/{project_slug}/versions/{version_id}/{experience_id}.yaml` |
| `task` | One execution's local lesson, usually a promotion candidate. | `.axis/experience/project/{project_slug}/tasks/{task_id}/{experience_id}.yaml` |

Promotion path:

```text
task -> version -> project -> team -> domain -> global
```

Promotion requires human approval at the target scope. Narrower approved experience wins when it conflicts with broader experience. Broader experience is fallback context, not an override of project or task constraints.

Experience lifecycle states:

| State | Meaning | Loadable By Default |
| --- | --- | --- |
| `candidate` | Raw candidate produced by an execution report. | no |
| `triaged` | Candidate passed basic dedupe and quality checks. | no |
| `approved` | Reviewed and approved for skill loading. | yes, until expired or deprecated |
| `merged` | Folded into another experience card. | no |
| `duplicate` | Rejected because an equivalent approved card already exists. | no |
| `stale` | Past TTL or invalidated by newer project/version facts. | no |
| `deprecated` | Retained for history but no longer recommended. | no |
| `rejected` | Reviewed and rejected as low-signal or unsafe. | no |

Cold-start and purification rules:

- If no approved cards match the execution context, the loader returns an empty set and records `experience_load_result: cold_start`; it must not generate synthetic experience to fill the gap.
- Each execution pack must set `experience_candidate_policy.max_candidates`; v0.1 default is `3`.
- A candidate must include `dedupe.fingerprint`, `dedupe.cluster_id`, `quality.evidence_count`, `quality.novelty`, and `lifecycle.expires_at`.
- Candidates with `quality.evidence_count < 1`, `quality.novelty: low`, or missing validation evidence must be `rejected` or left as `candidate`; they are not loadable.
- Duplicates are handled by setting `status: duplicate` and `dedupe.duplicate_of`; similar candidates can be grouped under the same `dedupe.cluster_id`.
- TTL expiration marks a card `stale`; stale cards are retained but excluded from default skill loading.

Skill loading strategy:

1. Load only `status: approved` cards unless the execution pack explicitly allows review candidates.
2. Filter by public-safety fields; reject cards with credentials or private URLs.
3. Exclude `approved` cards whose `lifecycle.expires_at` is in the past.
4. Match cards by `skill_hints`, `domains`, `project_slug`, `version_id`, and task tags.
5. Load in deterministic precedence: `task`, `version`, `project`, `team`, `domain`, `global`.
6. If two cards conflict, keep the narrower card and cite both IDs in the execution report.
7. Cap loaded cards by the execution pack's `skill_loading.max_cards`.

Experience Usage Flow:

1. Resolve the tool or skill from the execution pack's `tool_refs` / `skill_refs` and the Tool / Skill Catalog.
2. Read the catalog entry's `canonical_family`, `capability_tags`, `input_document_types`, and `experience_consumes_scopes`.
3. Match approved, non-stale experience cards by task context, document refs, capability tags, `skill_hints`, domain tags, project slug, version ID, and allowed scopes.
4. Sort matches by scope precedence: `task`, `version`, `project`, `team`, `domain`, `global`.
5. Within the same scope, prefer exact `skill_hints` match, then exact `capability_tags` match, then newer approved cards.
6. Truncate to `skill_loading.max_cards`; rejected or truncated cards must be counted with reasons in the execution report.
7. If no card remains after filtering, record `experience_load_result: cold_start` and continue without synthesized experience.
8. After execution, the tool or skill may only write `experience_card` candidates in the scopes allowed by `experience_candidate_outputs`.
9. Candidate cards must include dedupe, cluster, quality, lifecycle, and public-safety fields; they must not auto-promote to `approved`.
10. The execution report must record loaded card IDs, rejected card IDs/reasons, truncated count, conflict decisions, and candidate experience IDs.

### Agent Execution Protocol

Agent Execution Protocol defines the minimum package that can be handed to an agent. A request is executable only when the pack itself is `approved` and every referenced source document is approved and checksum-pinned.

Minimum executable fields:

| Field | Rule |
| --- | --- |
| `schema`, `schema_version` | Must be `axis.agent_execution_pack` and `"0.1"`. |
| `pack_id` | Stable public-safe ID. |
| `status` | Must be `approved` before execution. |
| `objective` | Concrete task goal. |
| `scope` | Project, version, task, and explicit out-of-scope boundaries. |
| `approved_document_refs` | Documents to execute, each with `doc_id`, `doc_type`, `revision`, `path`, and `content_sha256`. |
| `workflow_ref` | Optional workflow template/run reference. |
| `tool_refs`, `skill_refs` | Optional Tool / Skill Catalog refs that identify allowed executable capabilities. |
| `constraints` | Public-safety, implementation, permission, and no-expansion constraints. |
| `allowed_actions` | File edits, commands, issue comments, PR creation, or report-only behavior. |
| `skill_loading` | Allowed scopes, required cards, max cards, and conflict rule. |
| `retry_context` | Attempt number and links to previous failed or partial reports. |
| `public_safety_validation` | Required validators and latest validation status before execution. |
| `experience_candidate_policy` | Maximum candidates and minimum signal required for generated experience. |
| `code_map_policy` | Whether code-map changes must be reported as deltas or may create a review revision. |
| `acceptance_criteria` | Verifiable completion criteria. |
| `expected_outputs` | Required execution report and optional experience candidates. |

Example execution pack:

```yaml

  project_slug: demo-project
  version_id: v0.1
  task_id: task_protocol_design
  in_scope:
    - Document Protocol
    - Workflow Protocol
    - Experience Protocol
    - Agent Execution Protocol
  out_of_scope:
    - Implementing OSS upload
    - Changing credential handling
    - Adding runtime workflow scheduling
approved_document_refs:
  - doc_id: doc_demo_project_brief_v001
    doc_type: project_brief
    revision: 1
    path: .axis/docs/projects/demo-project/project.brief.yaml
    content_sha256: "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  - doc_id: doc_demo_version_plan_v001
    doc_type: version_plan
    revision: 1
    path: .axis/docs/projects/demo-project/versions/v0.1/plan.yaml
```

- `pack_id`, `run_id`, and executed document refs;
- used `tool_refs` / `skill_refs` and resolved catalog entries;
- summary of work completed;
- validation evidence;
- files changed or documents produced;
- acceptance result;
- product conflicts or pending decisions;
- experience candidates, if any;
- retry/resume context if execution was partial, blocked, or retried;
- `code_map_delta` if mapped code structure changed;
- experience candidate dedupe, quality, and lifecycle decisions;
- public-safety statement.

### End-to-End Examples

#### New Project Flow

1. Human creates `.axis/docs/projects/demo-project/project.brief.yaml` as `project_brief` with `status: draft`.
2. Human reviews and approves the project brief; status becomes `approved` and checksum is pinned.
3. Workflow run `project_create` requires an approved `version_plan` for `v0.1`.
4. Human approves `.axis/docs/projects/demo-project/versions/v0.1/plan.yaml`.
5. Human approves `pack_demo_initial_scaffold_v001.execution-pack.yaml`.
6. Agent loads the approved pack, approved refs, and matching experience cards.
7. Agent executes only the approved scope and writes an `execution_report`.
8. Reusable lessons are written as `task` experience candidates, then optionally promoted to `version` or `project`.
9. A WHA-9 package may summarize the report and experience in the four-file package; the OSS publisher uploads it without interpreting workflow state.

#### Existing Project Import Flow

1. Human starts `project_import` with a public-safe import boundary.
2. Agent or human writes a `project_brief` containing the code map: modules, entrypoints, contracts, test commands, and known unsafe/private paths to exclude.
3. Human approves import decisions as `decision_record` documents.
4. An approved execution pack authorizes only documentation and code-map updates.
5. Agent produces an `execution_report` with import findings and a `project` experience candidate for future tasks.
6. Version-specific follow-up work starts only after a `version_plan` is approved.

#### Version Iteration Flow

1. Human creates `.axis/docs/projects/demo-project/versions/v0.2/plan.yaml` with goals, non-goals, acceptance criteria, and linked decisions.
2. Required decisions are approved as `decision_record` documents.
3. Workflow run `version_iteration` breaks the plan into approved execution packs.
4. Agents execute packs independently, each producing an execution report.
5. Completed reports update the version evidence list; failed reports create a new decision or revised execution pack instead of mutating the approved pack.
6. Task experience candidates are promoted to `version` after review; only stable lessons are promoted to `project`, `team`, `domain`, or `global`.
7. Release/retrospective workflow reads the version plan, reports, and promoted experience to decide whether the version is complete.

## Technical Design

### Repository Paths

v0.1 reserves these public-safe repository paths:

```text
.axis/docs/projects/{project_slug}/project.brief.yaml
.axis/docs/projects/{project_slug}/versions/{version_id}/plan.yaml
.axis/docs/projects/{project_slug}/decisions/{decision_id}.yaml
.axis/docs/projects/{project_slug}/agents/{pack_id}.execution-pack.yaml
.axis/docs/projects/{project_slug}/reports/{run_id}.{report_type}.yaml
.axis/workflows/templates/{workflow_type}.workflow.yaml
.axis/workflows/runs/{run_id}.workflow-run.yaml
.axis/experience/{scope}/...
```

These paths are source-document paths, not WHA-9 outbox package paths. `.axis/outbox/` remains local-only and package staging only.

### Shared Schema Primitives

All four protocols use:

- `schema`: protocol schema name;
- `schema_version`: `"0.1"`;
- `status`: protocol-specific state;
- `storage.path`: repo-relative public-safe path;
- `storage.content_sha256`: checksum for approved executable documents;
- `owner.role`: role label, not a permission grant;
- `public_safety.reviewed`: required before execution or publishing;
- `public_safety.contains_credentials`: must be `false`;
- `public_safety.contains_private_urls`: must be `false`;
- `public_safety.validation.status`: `unchecked`, `passed`, or `failed`;
- `public_safety.validation.validators`: deterministic checks and manual review labels that were applied;
- `public_safety.validation.findings_count`: number of unresolved findings;
- `supersedes`: previous doc/revision ID when a new approved revision replaces it.

### Public-Safety Validation Patch

Public-safety validation is a required protocol gate, not an implementation of a new security platform. v0.1 requires deterministic static checks plus explicit review metadata. LLM review may assist triage, but it must not be the only reason `public_safety.validation.status` becomes `passed`.

Required validation fields:

| Field | Rule |
| --- | --- |
| `public_safety.validation.status` | `unchecked`, `passed`, or `failed`. Approved/executable/publishable documents require `passed`. |
| `public_safety.validation.validators` | List of applied checks, for example `deterministic_secret_scan`, `private_url_scan`, `entropy_scan`, `manual_public_safe_review`. |
| `public_safety.validation.findings_count` | Must be `0` when status is `passed`. |
| `public_safety.validation.validated_at` | UTC timestamp of the latest validation. |
| `public_safety.validation.validated_by.role` | Role label for the validator or reviewer. |
| `public_safety.redaction_notes` | Public-safe summary of what was redacted or why nothing was redacted. |

Validation responsibility boundaries:

| Stage | Responsible Protocol/Actor | Required Behavior | Not Responsible For |
| --- | --- | --- | --- |
| Document authoring | Document Protocol producer | Run deterministic static checks before a document can move from `draft` to `review`. | Central scanner service or permissions. |
| Document approval | Human/document owner role | Confirm validation status is `passed` before setting `approved`. | Creating secrets policy or granting access. |
| Agent execution | Agent Execution Protocol consumer | Refuse packs or approved refs whose validation status is not `passed`. | Rewriting source docs to hide findings unless explicitly allowed. |
| Package staging | Producing skill | Ensure package `metadata.json`, `report.md`, and `experience.md` are public-safe before `local_ready`. | Uploading or remote lifecycle management. |
| OSS publishing | `axis-ops-oss-publish` | Enforce WHA-9 package public-safety fields and fail upload when package metadata says unsafe. | Semantically approving protocol documents or scanning repo source paths. |

Failure rules:

- `unchecked` validation blocks approval and execution.
- `failed` validation blocks approval, execution, and publishing.
- A package with `contains_credentials: true`, `contains_private_urls: true`, or unresolved findings must not reach `local_ready`.
- If a finding is redacted, the document must get a new checksum and revision before it can be approved.
- A reviewer may add notes, but v0.1 has no waiver state; unresolved findings remain blocking.

### Manifest and Metadata Requirements

WHA-9 remains the package source of truth. The four protocols add optional index fields only. A v0.1 producer may include these fields in `metadata.json` or `manifest.json`; a v0.1 OSS publisher must not require them to upload a package that otherwise satisfies WHA-9.

Publisher boundary:

- validates JSON syntax, checksums, package files, release channel, and public-safety fields required by WHA-9;
- may preserve optional protocol fields unchanged;
- may preserve optional `tool_refs` and `skill_refs` unchanged;
- must not approve documents, promote experience, advance workflow state, schedule tools, or decide whether an agent may execute a pack.

Consumer boundary:

- reads `manifest.json` as package source of truth;
- treats optional protocol fields as discovery hints;
- treats optional `tool_refs` and `skill_refs` as catalog hints, not mandatory execution dependencies;
- follows repo source documents or package snapshots for semantic decisions.

### Idempotency and Consistency

- `doc_id`, `workflow_id`, `experience_id`, and `pack_id` are stable identities.
- `tool_id` and `skill_id` are stable catalog identities; only one active catalog entry is allowed for the same ID in one catalog version.
- An approved document is immutable; changes produce a new revision.
- `content_sha256` is required for any document referenced by an approved execution pack.
- Re-running an execution pack must produce a new `run_id` and report; it must not overwrite the old report.
- Experience promotion creates a new card at the target scope and links to the source card; it does not move the source file.
- Experience dedupe is based on `dedupe.fingerprint`; cards with the same fingerprint cannot both be approved for the same scope.
- Experience clustering is advisory metadata through `dedupe.cluster_id`; it groups related cards but does not create a central clustering service.
- Expired or stale experience cards remain in history but are excluded from default loading.
- A narrower approved experience card overrides a broader card only for the matching execution context.
- Code-map updates create deltas or new document revisions; approved project briefs are not mutated in place.
- Same-pack retry is idempotent only when approved refs, checksums, scope, and acceptance criteria are unchanged.
- A deprecated catalog entry remains readable for history but is excluded from default matching unless an execution pack pins it explicitly.
- A replaced catalog entry must point to `replaced_by`; consumers should resolve to the replacement for new execution packs.
- The repo source document is the source of truth for protocol state. A WHA-9 package is a published snapshot and discovery record.

### Failure Rules

| Failure | System Handling |
| --- | --- |
| Draft or review document referenced by an execution pack | Refuse execution and report missing approved source. |
| Checksum mismatch on an approved document | Refuse execution; require a new approved revision or corrected pack. |
| Missing required workflow output | Mark workflow run `blocked`; do not infer completion from package upload. |
| Workflow blocked by retryable external failure | Create a new execution `run_id` with `retry_of_run_id`; keep the same immutable pack only if retry policy allows it. |
| Workflow blocked by changed scope, refs, or acceptance criteria | Mark `resume_pending`; require a new approved execution pack. |
| Execution pack references an unknown active tool or skill | Mark the pack invalid until the catalog ref is corrected or removed. |
| Execution pack references a deprecated tool without explicit pinning | Refuse default selection and require an active replacement or explicit compatibility reason. |
| Experience conflict across scopes | Use narrower approved card; list conflict in execution report. |
| Experience candidate duplicates an approved card | Mark candidate `duplicate`, set `dedupe.duplicate_of`, and exclude it from skill loading. |
| Experience candidate is low-signal or lacks evidence | Keep it as `candidate` or mark `rejected`; do not promote or load it. |
| Experience card TTL expires | Mark `stale` and exclude from default loading. |
| Public-safety field fails | Refuse execution or publishing depending on where the failure is found. |
| Public-safety validation is unchecked | Block approval, execution, and publishing until validation is passed. |
| Agent partially completes work | Produce an execution report with `status: partial`; do not mark workflow completed. |
| Code structure changes without `code_map_delta` | Mark execution `partial` or `failed`; block the workflow with `code_map_delta_missing`. |
| OSS upload fails | WHA-9 package state becomes `failed`; protocol source documents remain unchanged. |

### Observability

Each execution report should record:

- pack ID, run ID, agent family, and timestamp;
- approved document refs with checksums;
- loaded experience card IDs and scope;
- files/documents produced;
- validation commands and summarized results;
- public-safety validators and findings count;
- acceptance criteria result;
- retry/resume fields: attempt, retry source, checkpoint, blocked reason;
- resolved tool/skill catalog entries and deprecated/replacement decisions;
- experience load result, loaded card IDs, rejected card reasons, truncated count, rejected candidate counts, duplicate counts, and stale counts;
- code-map status and any `code_map_delta`;
- pending product decisions;
- public-safety result.

Metrics are not required in v0.1, but future tooling can count protocol documents by `schema`, `status`, `project_slug`, `version_id`, `pack_id`, and `experience.scope`.

### Rollout and Rollback

Rollout:

1. Add this protocol document as the v0.1 design source.
2. Keep WHA-9 package files and OSS publisher unchanged.
3. Let WHA-10 use the optional manifest/metadata fields as additive indexes.
4. Introduce validators later without changing the frozen field names.

Rollback:

- Ignore optional protocol fields in `manifest.json` and `metadata.json`.
- Continue using WHA-9 four-file packages.
- Keep source protocol documents in repo history; mark superseded protocol docs as `archived` only through a new approved revision.

### Test Scope

v0.1 validators should eventually cover:

- every example parses as YAML or JSON;
- every required `schema_version` is `"0.1"`;
- execution packs with non-approved refs are rejected;
- execution packs with checksum mismatch are rejected;
- experience loading order is deterministic;
- experience candidate dedupe rejects same-scope duplicate fingerprints;
- expired or stale experience cards are excluded from default loading;
- blocked workflow runs expose `blocked_reason`, checkpoint, and retry/resume policy fields;
- same-pack retry is rejected when scope, approved refs, or acceptance criteria changed;
- code-changing reports include `code_map_delta` when mapped paths change;
- catalog examples include `tool_id` or `skill_id`, `canonical_family`, input/output document types, experience scopes, status, owner, and replacement fields;
- manifest optional `tool_refs` and `skill_refs` are accepted but not required;
- manifest optional fields are accepted but not required;
- publisher tests prove optional protocol fields do not alter upload order;
- public-safety checks reject credentials, private URLs, raw secrets, unchecked validation, and unresolved findings.

## Pending Product Decisions

These items are intentionally not resolved in this v0.1 design because resolving them would expand scope beyond the issue boundary:

1. Whether raw protocol source documents should be published as standalone OSS objects. v0.1 keeps WHA-9's four-file package and uses optional indexes/snapshots only; standalone raw document publishing requires a new package version or an explicit compatibility decision.
2. Where cross-project `global`, `domain`, and `team` experience should physically live. v0.1 freezes logical scopes and path shapes; a central registry, shared repo, or project-local mirror is a product/platform decision.
3. Who has authority to approve documents, promote experience, and mark workflows complete. v0.1 records owner and status fields but does not introduce roles, permissions, or approval services.
4. Whether Workflow Protocol should later become an executable orchestration runtime. v0.1 treats workflows as approved documents and does not enqueue agents or schedule work.
